# กรอบงาน UI/UX ของ Drum Pro

> **ใช้คู่กับ `ui-ux-pro-max` ที่ติดตั้งไว้ใน repo นี้แล้ว**
> (`.claude/skills/ui-ux-pro-max/` — คลังความรู้ดีไซน์ทั่วไป ค้นด้วย CLI ของมันเอง)
> **เมื่อสองอันขัดกัน ให้ยึดอันนี้**

## ใช้คลัง ui-ux-pro-max ยังไงให้ได้ของดีและไม่โดนมันพาออกนอกทาง

```bash
python3 .claude/skills/ui-ux-pro-max/scripts/search.py "<คำค้น>" --domain ux
```

**ดึงมาใช้ได้เลย** — `--domain ux` (เกณฑ์ขนาดเป้าแตะ โฟกัส คอนทราสต์ กฎ accessibility),
`--domain icons`, คำแนะนำเรื่อง performance และ "Common Rules for Professional UI"
ใน `references/pro-rules.md` พวกนี้เป็นความรู้สากล ใช้กับโปรแกรมนี้ได้ตรง ๆ

**อย่าเอามาใช้ตรง ๆ** — `--design-system`, `--domain color`, `--domain landing`,
`--domain typography` ลองรันกับโจทย์ของโปรแกรมนี้แล้วมันตอบว่าให้ทำ
**Hero-Centric Design + CTA + จานสีชมพู #EC4899 กับฟ้า #2563EB**
ซึ่งผิดทางทั้งหมด เพราะคลังมันสร้างจากงาน landing page และเว็บขายของเป็นหลัก
โปรแกรมนี้เป็นเครื่องมือทำงานที่มีกริดเป็นหัวใจ ไม่มี hero ไม่มี CTA
และมีโทนสีที่จูนมาแล้ว (ดูข้อ 2) **ห้ามเปลี่ยนจานสีตามที่มันเสนอ**

ถ้าจะใช้ `--design-system` จริง ให้ตั้ง `--density 8` ขึ้นไป (มือกลองต้องเห็นของเยอะ
พร้อมกัน) `--variance` ต่ำ (เครื่องมือทำงานไม่ต้องการ layout หวือหวา) แล้วอ่านเอา
เฉพาะส่วน accessibility กับ interaction ที่เหลือข้าม

โปรแกรมนี้คือ **เครื่องมือถอดจังหวะกลองสำหรับนักดนตรี** ไม่ใช่เว็บแอปทั่วไป
คนใช้คือมือกลอง/ครูสอนกลอง ที่นั่งถือ iPad กับปากกา แล้วถอดเพลงทีละห้อง
เขาเทียบหูกับสิ่งที่เห็นบนกริดตลอดเวลา ฉะนั้น**กริดคือโปรแกรม** ที่เหลือคือของประกอบ

## 0. งาน UI เก็บไว้ที่ไหน — ตัดสินไปแล้ว ทำตามนี้ได้เลย

**แก้ใน `index.html` ได้ตรง ๆ** งานจะไม่หายเมื่อผู้พัฒนาส่งไฟล์รุ่นใหม่มา
เพราะ repo รับรุ่นใหม่ด้วยการ **merge** ไม่ใช่เขียนทับ

```
upstream/klong-pro.html   ไฟล์ดิบรุ่นล่าสุดที่รวมแล้ว = จุดอ้างอิง (merge base)
index.html                ของจริง = ต้นฉบับ + ชั้นเว็บแอป + งาน UI
```

รุ่นใหม่มาเมื่อไหร่ `tools/merge-upstream.py` จะเทียบสามทางแล้วรวมให้
ส่วนที่คนละที่กันรวมเองได้ ส่วนที่แก้ทับที่เดียวกันมันจะหยุดและเตือน
(ทดสอบแล้วว่าใช้ได้จริง — ดูข้อ 6 ของ README)

**แปลว่าตอนทำงาน UI ไม่ต้องถามเรื่องนี้อีก ลงมือได้เลย** แต่มีสองข้อที่ยังจริงอยู่

* **อย่าแก้บล็อกชั้นเว็บแอป** (ส่วนที่คอมเมนต์ว่า "ชั้นเว็บแอป" ใน `<head>`
  ท้าย `<style>` และก่อน `</body>`) ถ้าต้องเปลี่ยนจริง ให้ไปแก้ที่
  `tools/apply-webapp-layer.py` ด้วย ไม่งั้นคนที่เริ่มใหม่จากศูนย์จะได้ของไม่ตรงกัน
* **ยิ่งแก้ CSS ส่วนที่ผู้พัฒนาชอบแก้ ยิ่งมีโอกาสชนตอน merge**
  ถ้าเลือกได้ ให้เพิ่มกฎใหม่ต่อท้ายแทนการแก้กฎเดิมกลางไฟล์ — ผลเหมือนกัน
  แต่ merge สะอาดกว่ามาก (CSS กฎหลังชนะกฎก่อนที่ specificity เท่ากัน)

## 0.5 ธีมที่ใช้อยู่ — มิดเซนจูรี่ กลางวัน/กลางคืน (ผู้ใช้เลือกแล้ว)

งานหน้าตาทั้งหมดอยู่ใน `theme/` ไม่ได้อยู่ในโค้ดของแอป

| ไฟล์ | ทำอะไร |
|---|---|
| `theme/klong-theme.css` | ตัวแปรสีสองโหมด ปุ่มนูน ถาดปุ่ม แถบไม้ ขอบทองเหลือง LCD แถบบนสองแถวบน iPad แนวตั้ง |
| `theme/klong-theme.js` | **ตัวแปลงสีบน canvas** + สวิตช์แสง + ไฟจังหวะ + มาตรวัด + ปุ่มยุบตามนิ้ว |
| `fonts/prompt*.woff2` | ฟอนต์ชื่อโปรแกรม เลขห้อง นาฬิกา |

โค้ดวาดกริดของแอปฝังสีไว้ราว 80 จุด ธีมไม่ได้แก้จุดพวกนั้น แต่ดักตอนตั้ง
`fillStyle`/`strokeStyle` บน canvas ที่อยู่บนจอแล้วแปลงตามตาราง `MAP`/`LANE`
canvas ของการส่งออก PDF/รูปไม่ได้ติดบนหน้า (`isConnected` เป็น false) จึงไม่โดนแปลง

แก้โค้ดแอปไปแค่สองจุด (มีคอมเมนต์ "ธีม" กำกับ):
`VOICES` ไฮแฮตเป็น `#4FC8D4` แยกจากสี "ตัวที่เลือก" `#4FC7D4` และไฟห้องใน `drawHead()`

**เมื่อรับไฟล์รุ่นใหม่แล้ว smoke-test ฟ้อง "สีบนจอที่ธีมยังไม่รู้จัก"**
แปลว่าผู้พัฒนาเพิ่มสีใหม่ในโค้ดวาด ให้หาว่าสีนั้นใช้วาดอะไร แล้วเพิ่มลงใน `MAP`
ของ `klong-theme.js` ทั้งค่ากลางวันและกลางคืน อย่าปิดเทสต์นี้ — สีที่หลุดจะโผล่เป็นสีเดิม
ของโปรแกรม (โทนน้ำตาลเข้ม) กลางหน้าจอธีมครีม ซึ่งเห็นชัดมากในโหมดกลางวัน

กฎของธีมที่ต้องรักษา: เขียวหัวเป็ด (`--ok`) ใช้บอก "ตัวที่เลือก/หัวอ่าน" อย่างเดียว ·
ไม่มีขาวล้วนหรือดำสนิท · ปุ่มที่เลือกต้องค้างลงและมีไฟเขียว (บอกสถานะด้วยรูปทรง) ·
ห้ามใช้ Prompt กับตัวเลขที่เปลี่ยนตอนเล่น (นาฬิกา ตัวนับ) เลขของ Prompt กว้างไม่เท่ากัน
และ `tabular-nums` ไม่มีผล กล่องจะหดขยายทุกเฟรม ดันปุ่มทั้งแถวสั่น (ผู้ใช้เจอจริงบน iPad)
ใช้ IBM Plex Sans Thai ซึ่งเลขกว้างเท่ากัน ชุดทดสอบมีเคสวัดความกว้างนาฬิกาอยู่แล้ว

## 1. ลำดับการทำงาน — วิเคราะห์ให้จบก่อนค่อยแตะโค้ด

ข้ามขั้นไหนไม่ได้ เหตุผลคือ UI ตัวนี้ถูกจูนมาแล้วโดยคนที่เล่นกลองเป็น
สิ่งที่ดู "รก" จากสายตาคนนอก หลายอันคือของที่มือกลองต้องเอื้อมถึงภายในหนึ่งวินาที
ถ้ารีบจัดระเบียบโดยไม่เข้าใจก่อน จะได้ UI ที่สวยขึ้นแต่ใช้ทำงานจริงไม่ได้

1. **วิเคราะห์ UX ปัจจุบัน** — เปิดของจริงด้วย `tools/smoke-test.js` หรือ Playwright
   ถ่ายภาพหน้าจอทั้งขนาด iPad และมือถือ ดูว่าอะไรอยู่ตรงไหนและทำไม
2. **ระบุปัญหา usability** — เขียนเป็นข้อ ๆ พร้อม**หลักฐาน** (พิกัด ขนาดจริง ภาพ)
   ไม่ใช่ความรู้สึก "มันดูรก" ใช้ไม่ได้ ต้องเป็น "ปุ่ม X สูง 24px ต่ำกว่าเกณฑ์แตะ 44px"
3. **วิเคราะห์ information hierarchy** — อะไรต้องเห็นตลอด อะไรเห็นเมื่อต้องใช้ อะไรซ่อนได้
   เกณฑ์ตัดสินคือ **ความถี่ในการใช้ระหว่างถอดเพลงหนึ่งท่อน** ไม่ใช่ความสำคัญเชิงแนวคิด
4. **เสนอ Design System** — ดูข้อ 2 ของเอกสารนี้ ของที่มีอยู่แล้วคือฐาน ไม่ใช่สิ่งที่ต้องรื้อ
5. **เสนอ component structure** — ดูข้อ 3
6. **ให้ผู้ใช้เห็นชอบก่อน แล้วค่อยลงมือ**

ข้อ 1–5 ส่งให้ผู้ใช้ดูก่อนเสมอ งาน UI ที่ทำไปแล้วแก้กลับยากกว่างานหลังบ้านมาก
และผู้ใช้คนนี้เป็นคนเล่นกลอง เขาตัดสินได้เร็วกว่าเราว่าอะไรใช้จริงไม่ได้

## 2. Design System — มีอยู่แล้ว ให้ต่อยอด อย่ารื้อ

โทนปัจจุบันคือ **ห้องอัดตอนกลางคืน** — น้ำตาลเทาเข้มอมอุ่น ไม่ใช่เทาน้ำเงินแบบ dashboard
นี่คือสิ่งที่ทำให้มันไม่หน้าตาเหมือนของที่ AI ปั๊มออกมา **อย่าเปลี่ยนเป็นเทาน้ำเงิน**

```css
--bg:#1F1B19  --panel:#2A2422  --panel2:#332B28       /* พื้น → แผง → แผงซ้อน */
--line:#453B37  --line2:#5A4C46                        /* เส้นคั่น → เส้นเน้น */
--ink:#EFE7DE  --dim:#A2948B  --dimmer:#6F625B         /* ตัวอักษร 3 ระดับ */
--ok:#4FC7D4   /* ฟ้า = สิ่งที่เลือกอยู่ / ทำได้ */
--warn:#E2564A /* แดง = ผิดกฎโน้ต / mute */
--soft:#E0A64A /* ส้ม = solo / เตือนเบา */
--rowh:27px  --labelw:132px  --head:46px               /* มาตรวัดของกริด */
```

กฎการใช้สี: **สีมีความหมายเดียวทั้งโปรแกรม** ฟ้าแปลว่า "อันนี้แหละ" เสมอ
ถ้าเอาฟ้าไปใช้ตกแต่งเฉย ๆ สายตาจะเลิกเชื่อสีฟ้า แล้วตัวบ่งชี้ทั้งระบบจะพังพร้อมกัน

ฟอนต์คือ IBM Plex Sans Thai เก็บในโปรเจกต์ (`fonts/`) **ห้ามเพิ่มฟอนต์จากเน็ต** — ดูข้อ 5

สิ่งที่ยังขาดและเพิ่มได้ ถ้าเพิ่มให้ประกาศเป็นตัวแปรที่ `:root` ไม่ใช่ค่าดิบกระจายในไฟล์:
ระยะห่างเป็นขั้น (4/8/12/16), รัศมีมุม (ตอนนี้มี 5–10px ปนกันอยู่), ขนาดตัวอักษรเป็นขั้น,
และ `--tap:44px` สำหรับขนาดเป้าแตะขั้นต่ำ

## 3. โครง component ที่มีอยู่จริง

อ่าน `references/ui-map.md` เพื่อดูผังเต็มว่า id ไหนทำอะไร
สรุปที่ต้องรู้ก่อนแตะ:

```
header            หัวเรื่อง — ซ่อนเมื่อ body.locked
main.wrap
  #drop           รับไฟล์เสียง
  .panel × 7      pGrab pGenre pGrid pNote pSave pCheck pDet — ซ่อนเมื่อ body.locked
  #gw             ★ กริด = หัวใจ
    #gs           ตัวเลื่อนแนวนอน
      canvas      วาดทั้งหมดด้วยมือ (ไม่ใช่ DOM) — position:sticky
    #labels       ชื่อเสียงกลองด้านซ้าย ทับบน canvas
    #zwheel       วงล้อซูม
#tp               transport bar — position:fixed bottom เสมอ แม้ body.locked
#pop              popup แก้ค่าโน้ตทีละตัว
```

`body.locked` = โหมดโฟกัส ซ่อนทุกอย่างยกเว้นกริดกับ `#tp`
**เป็นฟีเจอร์สำคัญ อย่าทำพัง** — มันคือท่าที่คนใช้จริงตอนถอดเพลงยาว ๆ

**อย่าสร้าง component ใหม่ที่ซ้ำของเดิม** ก่อนเพิ่มปุ่มหรือแผง ให้หาก่อนว่ามี
`.btn` `.btn.sm` `.seg` `.field` `.valwrap` `.chk` `.panel` อยู่แล้วหรือยัง

## 4. กริดกับ playhead — ตรงนี้ห้ามพลาด

* **กริดเป็น canvas ที่วาดเองทั้งใบ** แก้หน้าตาของกริด = แก้โค้ดวาด ไม่ใช่ CSS
* **playhead ลากได้ที่แถบบนสุดของ canvas (`p.head && p.y<26`)** แล้วกดเล่นจะเริ่มจากตรงนั้น
  พฤติกรรมนี้คือสิ่งที่ผู้ใช้ขอมาตรง ๆ ถ้าแตะโค้ดแถวนี้ต้องทดสอบด้วยนิ้วจริงทุกครั้ง
* `canvas{touch-action:none}` ถูกตั้งไว้ล่วงหน้าโดยตั้งใจ เพราะ Safari จะหน่วงตอนต้นนิ้ว
  ถ้าต้องรอดูว่าจะ preventDefault ไหม **อย่าย้ายไปตั้งทีหลัง**
* เครื่องมือ: `pan` `draw` `select` `erase` `vel` — **Apple Pencil วางโน้ตได้เสมอ**
  ไม่ว่าเลือกเครื่องมือไหน (นิ้วเลื่อนจอ ปากกาเขียน — เป็นท่ามาตรฐานของแอปวาดบน iPad)
* การวาดใหม่ผ่าน `requestDraw()` ซึ่งรวบเป็นเฟรมละครั้ง เพราะอีเวนต์เลื่อนจอบน iOS
  ยิงถี่กว่าเฟรม **อย่าเรียก `draw()` ตรง ๆ ในตัวจัดการอีเวนต์** จะได้อาการสะดุดกลับมา

## 5. ข้อห้ามที่ทำให้ของพังเงียบ ๆ

**CSP ล็อกไว้ว่าโหลดได้จากตัวเองเท่านั้น** (`default-src 'self'`)
ฉะนั้น **ห้ามใส่ของจากข้างนอกทุกชนิด** — ฟอนต์ Google, icon จาก CDN, CSS framework, รูปจาก URL
เบราว์เซอร์จะบล็อกทิ้ง**เงียบ ๆ ไม่มี error ให้เห็น** หน้าเว็บจะพังแบบหาสาเหตุไม่เจอ
ต้องการ icon → วาดเป็น inline SVG ต้องการฟอนต์ → เอามาไว้ใน `fonts/`

ข้อห้ามอื่น:
* **ห้ามลบฟีเจอร์ที่ทำงานอยู่** ถ้าคิดว่าควรลบ ให้เสนอเหตุผลแล้วรอผู้ใช้ตัดสิน
* **ห้ามแก้ตรรกะ** ที่ไม่เกี่ยวกับหน้าตา งาน UI ควรเห็นได้ใน diff ว่าแตะแต่การแสดงผล
* **ห้ามเดามาตรฐานโน้ตกลอง** — ดูข้อ 6

## 6. มาตรฐานโน้ตกลอง — ของจริงอยู่ในโค้ดแล้ว

โปรแกรมนี้**เข้ารหัสมาตรฐานไว้ถูกต้องอยู่แล้ว** อย่าไปเขียนทับด้วยความจำของตัวเอง
แหล่งอ้างอิงในไฟล์คือ `const STAFF` (ประมาณบรรทัด 1618) ซึ่งกำหนด
ตำแหน่งบนบรรทัด 5 เส้นและรูปหัวโน้ตของแต่ละเสียง เช่น ฉาบเป็นกากบาท กลองเป็นหัวปกติ
ไฮแฮตเหยียบอยู่ใต้บรรทัด สแนร์อยู่ช่องที่ 3 — และ `headOf()` ที่บอกว่า
**หัวโน้ตเป็นผลของเสียง + ลูกเล่น ไม่ใช่ของเสียงอย่างเดียว** (ริมช็อต ครอสสติ๊ก เปลี่ยนหัวโน้ต)

ถ้างานต้องเพิ่มหรือเปลี่ยนสัญลักษณ์:
1. อ่าน `STAFF` / `ARTS` / `PALETTE` / `headOf()` / `xmlPitch()` ในไฟล์ก่อน
2. ถ้ายังไม่ชัด **ถามผู้ใช้ เขาเป็นมือกลอง** — เขาตอบได้ใน 10 วินาที
3. **ห้ามเดาจากความจำ** โน้ตกลองที่ผิดทำให้ไฟล์ที่ส่งออกไปใช้ซ้อมจริงผิดตาม
   ซึ่งแย่กว่าการถามมาก

## 7. แตะ / accessibility / performance

**แตะ** — เป้าแตะอย่างน้อย 44×44px บนจอสัมผัส (`@media (pointer:coarse)`)
ช่องกรอกบนจอสัมผัสต้อง `font-size:16px` ไม่งั้น Safari ซูมหน้าเองแล้วกริดหลุดมือ
(ตั้งไว้แล้วในชั้นเว็บแอป ถ้าเพิ่มช่องกรอกใหม่ต้องเข้าข่ายกฎนี้ด้วย)
เผื่อ safe-area ของรอยบาก/ขีดโฮมด้วย `var(--sat/--sab/--sal/--sar)` ที่ประกาศไว้แล้ว

**accessibility** — ของที่มีอยู่และต้องรักษาไว้: `aria-pressed` บนปุ่มสลับสถานะ,
`:focus-visible` เป็นกรอบฟ้า, `prefers-reduced-motion` ปิด transition
ที่ควรเพิ่มเมื่อมีโอกาส: `aria-label` บนปุ่มที่มีแต่ไอคอน, ประกาศสถานะเล่น/หยุดให้ screen reader,
และอย่าสื่อสารด้วยสีอย่างเดียว (แดง = ผิดกฎ ควรมีข้อความกำกับด้วย)

**performance** — กริดวาดด้วย canvas เฟรมละครั้งผ่าน `requestDraw()`
ระวังสองอย่าง: อย่าเพิ่มงานหนักในลูปวาด และอย่าทำให้ layout ถูกคำนวณใหม่ตอนเลื่อน
(อ่าน `offsetWidth`/`getBoundingClientRect` ในตัวจัดการ scroll = สะดุดทันทีบน iPad)

## 8. ทำเสร็จแล้วต้องพิสูจน์ว่าของเดิมยังทำงาน

แก้ UI แล้ว**ต้องรัน** ไม่ใช่อ่าน diff แล้วเชื่อ:

```bash
npm i playwright && node tools/smoke-test.js
```

ชุดนี้ตรวจว่าโปรแกรมเปิดขึ้น ฟอนต์มา ไม่มีคำขอออกนอกเครื่อง Service Worker คุมหน้า
**แตะนิ้ววางโน้ตได้ ส่งออก .mid/.musicxml ได้จริง กดเล่นแล้วเวลาเดิน** ตัดเน็ตแล้วยังเปิดได้
ไม่มี CSP violation และไม่มี error — ทั้งขนาดจอ iPad และมือถือ

ถ้างานแตะกริดหรือ playhead ให้**เพิ่มเคสลงใน smoke-test.js ด้วย** เช่น ลาก playhead
แล้วเช็คว่าเล่นเริ่มจากตำแหน่งนั้นจริง ของที่เทสต์ไม่ครอบคลุมจะพังเงียบ ๆ ในรอบถัดไป

และ**ดูด้วยตา** — จับภาพหน้าจอทั้งสองขนาดแล้วเทียบก่อน/หลัง ส่งให้ผู้ใช้ดู
ตัวเลขผ่านหมดแต่หน้าตาเพี้ยนเป็นเรื่องที่เกิดได้ง่ายมากในงาน UI
